How this is kept from touching anything

{% call u.caveat("A read-only attach is not enough") %}

On a scratch lake, with the lake attached read-only and DuckDB's configuration locked, SELECT * FROM ducklake_cleanup_old_files(...) deleted scheduled Parquet files before its catalog write failed. ATTACH of the catalog file for writing, COPY into the lake directory, and DETACH also succeeded. So the console does not rely on those settings alone.

{% endcall %}
  • Each query gets its own child process, one at a time, at low priority, stopped at 10 seconds. It holds no API keys and reads no settings file.
  • The statement is parsed first. It must be one SELECT or a plain EXPLAIN of one, and it may call only the table functions on a short list. Everything else is rejected before it runs.
  • The child runs inside a macOS sandbox that denies all network access and every file write, except the catalog's -shm and -wal files, which a SQLite reader needs. So a statement that got past the parser check still could not delete or change a Parquet file or the catalog file.
  • DuckDB limits it to 2 threads and 1 GB, with no spill to disk and file reads confined to the lake directory.
  • The route answers loopback requests only, and every query is logged.

A test on a scratch lake runs each mutation attempt and checks that the catalog and the data files did not change. No mutation is ever tried on the real lake.
