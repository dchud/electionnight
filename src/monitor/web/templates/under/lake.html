DuckLake: what this system stores, from its own catalog

DuckLake is a table format with its metadata in a SQL database. Here that database is one SQLite file, the data is Parquet files beside it, and DuckDB is the engine that reads both. Everything below comes from the catalog, except the table map, which is declared in code, and where a table's rows are read. See also Inventory for rows against keys in every table, Storage for files, snapshots, and time travel, and Data model for a table as the code declares it.

The table map: how the tables relate

{% call u.caveat("These relations are not enforced") %}

DuckLake has no foreign keys, primary keys, or unique constraints. A line between two tables is a value the code keeps equal in both, and nothing checks it. A dashed line ending at gold is different: rollups read that table.

Tables are append-only, so a reader takes the newest row per record key. The record key differs by table, and it can differ from the key on the line. nlp.mentions joins raw.items on item_id, but its record key is mention_id: one item has many mentions, and each mention keeps its own newest row.

Every relation, as declared in code

Declared by hand and checked against the code that writes each table, not inferred from names. call_id on nlp.race_calls identifies a race call, and on nlp.llm_calls and nlp.llm_traces it identifies a model call.

This list covers every key between lake tables, including keys held in a list or in JSON and keys that hold only under a condition. The map draws the main ones. Kind counts records, the newest row per record key, not rows. The list leaves out three things: a gold table's bin_start, which is a time bucket; the state text the model writes on nlp.mentions and nlp.race_calls, which nothing keeps equal to ref.states; and labels such as parser, model, purpose, and language, which identify no record.
